# MISO 구조 보존 전처리기 개선 설계

- 작성일: 2026-07-29
- 상태: 사용자 방향 승인 완료, 서면 검토 대기
- 대상: 발전소 현장 직원과 신사업팀이 사용하는 Excel, PDF, Word, TXT/CSV 문서

## 1. 목적

이 앱은 범용 문서 분석기나 의미 기반 청킹 시스템을 만들지 않는다. MISO RAG에 문서를 등록하기 전에 문서의 명시적 구조를 이용해 `한 청크에 한 주제 또는 한 섹션`이 들어가도록 정리하는 것이 목적이다.

사용자는 AI와 청킹 원리를 알 필요가 없어야 한다. 파일을 올리고 문서 종류를 선택하면, 앱이 MISO에 안전하게 등록할 수 있는 TXT를 생성하고 처리하기 어려운 문서는 명확한 경고를 보여준다.

## 2. 확정된 MISO 계약

MISO의 사용자 설정은 다음과 같다.

- 사용자 정의 구분자: `@@@`
- 최대 청크 길이: 4,000자
- 처리 순서: `@@@`에서 우선 분할한 뒤, 나뉜 조각이 4,000자를 넘으면 MISO가 추가 분할

따라서 앱은 모든 최종 청크를 3,800자 이하로 완성한다. 200자는 문맥 머리말, 구분자 주변 개행, 문자 계산 방식 차이를 위한 안전 여유다. 4,000자는 앱이 활용할 목표 길이가 아니라 MISO의 최종 방어선이다.

구분자는 청크 사이에만 `\n@@@\n` 형태로 넣는다. 첫 청크 앞과 마지막 청크 뒤에는 넣지 않는다. 원문 본문, 파일명, 제목 등 최종 출력에 정확한 문자열 `@@@`가 있으면 `＠＠＠`로 바꾸고 사용자에게 충돌 해결 경고와 변경 건수를 표시한다.

## 3. 범위

### 포함

- 법령·사규, 표·엑셀, 설명서·업무 매뉴얼, 일반 문서·보고서의 유형별 구조 분할
- 공통 구조 보존 및 최종 길이 검증
- 현재 확인된 공백 소실, 반복 본문 오삭제, 4,000자 초과, 빈 결과 성공 처리 문제 수정
- SheetJS를 공식 0.20.3 배포본으로 업데이트
- UTF-8과 EUC-KR(CP949 호환) TXT/CSV 처리
- Mammoth.js를 이용한 DOCX 로컬 구조 추출
- 처리 결과 품질 경고와 MISO 예상 청크 요약
- 실제 현장 문서를 본뜬 골든 테스트와 회귀 테스트

### 제외

- 국가법령정보 OPEN API 연동
- 임베딩 또는 LLM을 이용한 의미 기반 청킹
- MISO 지식 저장소 직접 등록 API
- Docling, Unstructured, 별도 Python 서비스
- PDF.js를 이용한 PDF 파서 교체
- 스캔 PDF OCR 품질 자체 개선
- 복잡한 병합표나 다단 PDF를 완벽하게 재구성하는 기능

PDF와 이미지 문서는 현재 MISO 추출 경로를 유지한다. 앱은 추출 결과가 비어 있거나 지나치게 짧고 깨진 문자가 많은 경우 이를 조용히 성공시키지 않고 경고한다.

## 4. 핵심 설계 원칙

1. **강한 구조 경계를 넘어서 합치지 않는다.** 서로 다른 조문, 매뉴얼 절, Excel 시트, 명시적 제목 섹션은 한 청크에 섞지 않는다.
2. **작은 섹션을 길이 채우기 목적으로 합치지 않는다.** 600자 섹션은 600자 청크로 유지한다. 다만 내용이 없는 제목은 바로 뒤의 본문에 붙인다.
3. **긴 섹션만 내부 구조에서 다시 나눈다.** 법령은 항·호·목, 매뉴얼은 단계, 표는 행, 일반 문서는 문단과 문장 순서로 분할한다.
4. **고립된 청크에도 문맥을 남긴다.** 문서명, 상위 제목 경로, 시트명, 표 헤더를 짧게 반복한다.
5. **본문 오버랩은 기본적으로 사용하지 않는다.** 중복 본문 대신 문맥 머리말만 반복해 검색 노이즈를 줄인다.
6. **삭제보다 보존을 우선한다.** 페이지 경계와 위치 근거가 없는 반복 문구 제거는 하지 않는다.
7. **모든 최종 출력에 공통 안전 검사를 적용한다.** 유형별 처리 성공 여부와 관계없이 빈 청크, 길이 초과, 구분자 충돌을 마지막에 다시 확인한다.

## 5. 처리 구조

기존 외부 호출 형태는 유지하되 내부 처리를 작은 단위로 분리한다.

1. **입력 추출기**
   - XLSX/XLS/ODS: SheetJS Worker가 Workbook 구조를 읽는다.
   - TXT/CSV: ArrayBuffer를 UTF-8 또는 EUC-KR로 디코딩한다.
   - DOCX: Mammoth.js가 의미 구조 HTML을 생성하고, 앱은 제목·문단·목록·표 블록만 읽는다.
   - PDF/이미지/기타 Office: 현재 MISO 텍스트 추출 경로를 유지한다.
2. **공통 블록 변환기**
   - 제목, 문단, 목록 항목, 표, 표 행, 페이지 경계, 시트 경계를 내부 블록으로 표현한다.
   - 원문의 순서와 선행 들여쓰기를 보존한다.
3. **유형별 구조 청커**
   - 네 문서 유형의 강한 경계와 내부 분할 우선순위를 적용한다.
4. **문맥 부가 단계**
   - 각 청크에 필요한 최소 문서명과 상위 경로를 붙인다.
5. **공통 예산 및 검증 단계**
   - 문맥을 포함한 최종 문자열이 3,800자 이하인지 확인한다.
   - 초과 시 유형별 내부 경계에서 재분할하고, 마지막 수단으로 문장→공백→문자 경계를 사용한다.
6. **MISO TXT 직렬화 단계**
   - 검증된 청크만 `\n@@@\n`으로 연결한다.
   - 직렬화된 결과를 다시 분리해 개수, 빈 조각, 최장 길이, 구분자 충돌을 재검사한다.

긴 텍스트의 공백 기반 분할은 토큰을 다시 합칠 때 반드시 원래 공백을 복원한다. 단어를 붙여 의미를 바꾸는 분할은 허용하지 않는다.

### 5.1 내부 단계 간 계약

- `ExtractedDocument`: 파일명, 원본 형식, 순서가 있는 `DocumentBlock[]`, 추출 경고를 담는다.
- `DocumentBlock`: 고유 ID, 종류, 원문 텍스트, 상위 제목 경로, 시트/표 위치, 원본 순서를 담는다.
- `ChunkDraft`: 하나 이상의 블록 ID, 반복할 문맥, 본문을 담는다.
- `ValidatedChunk`: 최종 문자열, 문자 수, 포함한 블록 ID, 경고를 담는다.

모든 입력 블록은 최종 청크에 정확히 한 번 본문으로 소비돼야 한다. 제목 경로와 표 헤더만 문맥으로 반복할 수 있다. 페이지 머리글처럼 명시적으로 제거한 블록은 제거 사유와 개수를 경고 기록에 남긴다. 이 소비 기록을 이용해 누락과 의도하지 않은 본문 중복을 검출한다.

## 6. 유형별 최종 분할 규칙

### 6.1 법령·사규

- 기본 청크 단위는 `조`다.
- 편·장·절·관은 상위 경로로 저장하고 각 조문 청크에 반복한다.
- 조문이 3,800자를 넘을 때만 항→호→목→문장 순으로 나눈다.
- 분할된 후속 청크에도 법령명, 상위 경로, 조 번호와 조 제목을 반복한다.
- 부칙은 본칙과 분리한다.
- 별표·별지의 표는 표 전용 규칙으로 처리한다.
- 서로 다른 조문은 작아도 길이 채우기 목적으로 합치지 않는다.
- `제1조`, `제1조의2`, `①`, `1.`, `가.`와 Markdown 제목 표기를 인식한다.

### 6.2 표·엑셀

- 시트가 바뀌면 무조건 새 청크를 시작한다.
- 한 시트 안에서 빈 행 묶음과 헤더 후보를 이용해 여러 표를 구분한다.
- 같은 표의 행은 3,800자 예산 안에서 함께 배치한다.
- 모든 청크에 파일명, 시트명, 표 이름 또는 위치, 열 제목을 반복한다.
- 셀 안의 `|`, 개행, 쉼표, 따옴표를 보존하고 Markdown 표 표현에 필요한 이스케이프를 적용한다.
- 한 행이 예산을 넘으면 셀 단위로 나눈다. 긴 셀은 열 이름과 행 식별자를 반복한 뒤 문장 경계에서 나눈다.
- Workbook의 `!merges` 정보를 읽고 병합셀 수와 위치를 경고에 포함한다.
- 병합 헤더를 확신할 수 없으면 값을 임의로 복제해 사실을 만들지 않고 `원문 확인 필요`로 표시한다.
- SheetJS의 `sheet_to_csv`를 중간 표현으로 사용하지 않고 행·열 배열과 병합 범위를 유지한다.

### 6.3 설명서·업무 매뉴얼

- 번호 제목 아래의 절차 전체가 기본 청크 단위다.
- `1.`, `1)`, `1-1`, `가)`, `①`, `Step 1`, `단계 1`을 제목 또는 절차 표시로 인식한다.
- 섹션이 3,800자를 넘을 때만 작업 단계에서 나눈다.
- 후속 청크에 문서명과 현재 제목 경로를 반복한다.
- `주의`, `경고`, `위험`, `금지`, `확인`, `참고` 블록을 관련 작업 단계와 떨어뜨리지 않는다.
- 중첩 목록과 들여쓰기를 보존한다.
- 짧다는 이유로 서로 다른 작업 제목을 한 청크에 합치지 않는다.

### 6.4 일반 문서·보고서

- 명시적 제목 아래의 문단 묶음을 기본 섹션으로 본다.
- 제목이 없으면 문단을 원래 순서대로 3,800자 예산 안에서 묶는다.
- 새로운 명시적 제목이나 표 경계를 넘어서 합치지 않는다.
- 표는 공통 표 전용 규칙으로 처리하고 분할 시 헤더를 반복한다.
- 목록, 인용, 들여쓰기를 보존한다.
- 페이지 번호 근처라는 근거가 없는 반복 문구는 자동 삭제하지 않는다.

## 7. 파일 형식 개선

### 7.1 SheetJS 0.20.3

- npm 레지스트리의 오래된 `xlsx@0.18.5` 대신 SheetJS 공식 0.20.3 tarball을 고정 사용한다.
- 현재 Web Worker 구조는 유지한다.
- Worker 응답은 평탄화된 CSV 한 문자열이 아니라 시트명, 행 배열, 병합 범위, 경고를 포함하는 구조화 데이터로 변경한다.
- 날짜와 표시값은 사용자가 Excel에서 본 값에 가깝게 보존한다.

### 7.2 UTF-8/EUC-KR

- TXT/CSV는 `File.text()` 대신 ArrayBuffer로 읽는다.
- BOM이 있으면 BOM을 우선한다.
- BOM이 없으면 `TextDecoder('utf-8', { fatal: true })`로 먼저 검사한다.
- 엄격한 UTF-8 디코딩이 실패하면 `TextDecoder('euc-kr')`로 디코딩한다.
- 깨짐 문자인 `�`가 많거나 열 수가 불규칙하면 노란 경고와 인코딩 수동 선택을 제공한다.
- 자동 판정 결과가 정상인 경우에는 직원에게 인코딩 선택 UI를 노출하지 않는다.

### 7.3 Mammoth.js DOCX

- DOCX는 브라우저에서 Mammoth.js를 동적 로드해 로컬 구조 추출을 먼저 시도한다.
- Word의 Heading 스타일, 문단, 목록, 표를 내부 블록으로 변환한다.
- Mammoth가 생성한 HTML을 화면에 원문 그대로 주입하지 않는다. 지원하는 요소의 텍스트와 구조만 읽는다.
- DOCX가 손상됐거나 구조 추출에 실패하면 현재 MISO 추출 경로로 자동 전환하고 노란 경고를 표시한다.
- 파일에 Word 제목 스타일이 없으면 시각적 글꼴 크기를 억지로 해석하지 않고 일반 문단 규칙을 적용한다.

## 8. 사용자 화면

기존 네 가지 문서 종류 선택은 유지한다. XLSX/CSV는 표·엑셀을 자동 선택한다. DOCX/PDF는 이번 범위에서 유형 자동 판정을 추가하지 않고 사용자가 주된 구조에 가까운 유형을 선택한다.

`@@@`와 4,000자 설정은 현장 사용자가 실수로 바꾸지 않도록 고정 안내값으로 표시한다. 앱은 내부적으로 3,800자 안전 상한을 사용한다.

완료 화면에는 다음 항목만 명확하게 표시한다.

- MISO 예상 청크 수
- 가장 긴 청크의 문자 수
- 앱 안전 상한 3,800자 초과 청크 수
- 4,000자 초과 청크 수
- 원문 `@@@` 충돌 수
- 결과 상태: 등록 가능 / 원문 확인 필요 / 등록 불가

빨간 오류가 있으면 MISO 등록용 TXT 다운로드를 막지만, 원문 추출본 다운로드는 허용한다.

### 빨간 오류

- 결과가 비어 있음
- 최종 청크가 앱 안전 상한 3,800자를 초과함
- 직렬화 후 빈 청크 또는 해결되지 않은 구분자 충돌이 있음
- 입력 블록이 누락·중복 소비됐거나 단어가 붙는 보존성 검사가 실패함

### 노란 경고

- 병합셀, 열 수 불일치, 한 시트 안의 여러 표가 감지됨
- DOCX 로컬 추출이 실패해 MISO 추출로 전환됨
- PDF/Word 추출 결과가 지나치게 짧거나 깨진 문자가 많음
- 한 행 또는 한 절차가 안전 상한에 가까워 내부 분할됨
- 반복 머리글로 제거한 후보가 있어 원문 확인이 필요함

## 9. 테스트 및 검증

### 공통 불변식

- 모든 최종 청크는 문맥 머리말을 포함해 3,800자 이하
- `chunks.join('\n@@@\n').split('@@@')`의 조각 수가 원래 청크 수와 동일
- 직렬화 후 각 MISO 예상 조각은 4,000자 이하이며 비어 있지 않음
- 강한 구조 경계를 공유하지 않는 두 섹션이나 두 시트가 한 청크에 섞이지 않음
- 허용된 공백 정규화, 문맥 반복, 기록된 `@@@` 전각 치환을 제외한 본문 값이 원래 순서로 보존됨
- 모든 입력 블록 ID가 최종 본문에 정확히 한 번 소비되거나 명시적인 제거 사유를 가짐

### 필수 회귀 테스트

- 1,500개 단어가 있는 장문에서 단어 사이 공백이 사라지지 않음
- 같은 `주의 사항 / 전원을 차단` 문구가 세 번 등장해도 본문 세 건이 보존됨
- 4,100자 Excel 행이 3,800자 이하의 의미 있는 조각으로 분할됨
- 셀 안의 `|`, 개행, 쉼표, 따옴표가 보존됨
- 원문 `@@@`가 MISO 구분자로 오인되지 않음
- 빈 결과가 성공 처리되지 않음
- 한글, 이모지, LF/CRLF가 섞인 청크도 직렬화 후 MISO 상한을 넘지 않음

### 골든 문서

- 발전소 기동·정지·점검 매뉴얼 기본형과 장문형
- 2개 시트 단순 Excel과 병합셀·다중표·긴 셀 복잡 Excel
- 편·장·절·조·항·호·목·부칙·별표가 있는 법령/사규
- 제목·문단·표가 섞인 Word 및 PDF 추출 텍스트
- UTF-8 CSV, EUC-KR CSV, 깨진 문자 파일
- Heading 스타일·목록·표가 있는 DOCX와 스타일이 없는 DOCX

### 완료 기준

- 골든 문서의 본문 및 비어 있지 않은 Excel 셀 보존율 100%
- 3,800자 초과 최종 청크 0개
- 서로 다른 시트·조문·명시적 매뉴얼 절이 한 청크에 혼합된 사례 0개
- 모든 후속 분할 청크에 필요한 제목 경로 또는 표 헤더 존재
- 현장 직원이 완료 화면만 보고 `등록 가능`, `원문 확인 필요`, `등록 불가`를 구분할 수 있음

## 10. 구현 순서

1. 공통 길이 예산, 직렬화 검증, 본문 보존 문제와 빈 결과 처리
2. 법령·매뉴얼·일반 문서의 구조 경계와 문맥 반복
3. SheetJS 0.20.3 업데이트와 구조화된 Workbook Worker 응답
4. Excel 표·행 분할, 병합셀 경고, 표 헤더 반복
5. UTF-8/EUC-KR 디코딩 및 필요할 때만 보이는 수동 선택
6. Mammoth.js DOCX 로컬 추출과 MISO fallback
7. 완료 화면 상태·통계·경고 정리
8. 전체 골든 테스트와 로컬 MISO 계약 검증
9. MISO 접근이 가능한 환경에서 대표 TXT 한 건을 수동 등록해 실제 왕복 결과 확인

국가법령정보 OPEN API는 이 설계와 구현 범위에 포함하지 않는다.
